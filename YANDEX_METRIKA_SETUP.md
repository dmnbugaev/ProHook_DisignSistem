## 3. SPA-навигация без двойного учёта

Приложение — Nuxt/Vue Router (клиентские переходы без перезагрузки).
Реализована официальная рекомендация Метрики для SPA:

- первичный просмотр страницы учитывается самой `init` (при загрузке);
- `router.afterEach` досылает `ym(id, "hit", url, { title, referer })`
  только при фактической смене URL (сравнение `pathname+search`);
  referer — предыдущий внутренний адрес;
- исходный URL не пересылается hit'ом → ровно один просров на страницу;
- повторной `init` не происходит (закреплено тестом).

Санитайзер (`sanitizeEventParams`) отбрасывает ключи вне allowlist и
обрезает значения до 64 символов; содержимое полей форм и ПД не
передаются (юнит-тест «allowlist отрезает лишнее»).

**Цели в интерфейсе Метрики не создаются автоматически** — `reachGoal`
только отправляет события. Действие владельца: в настройках счётчика
113582832 создать цели типа «JavaScript-событие» с идентификаторами из
таблицы (рекомендуется начать с `store_phone_click`,
`contacts_page_view`, `store_location_view`).

## 7. Вебвизор, карта кликов, конфиденциальность

`webvisor: true`, `clickmap: true` включены по конфигурации владельца.
Раскрыты в политике ПД (п. 3.6). Действия владельца в интерфейсе счётчика:

1. Вебвизор → отключить «запись содержимого полей ввода» (по умолчанию
   выключено — проверить), чтобы ФИО/телефоны форм гарантированно не
   попадали в записи.
2. Убедиться, что включена маскировка стандартных чувствительных полей.
3. При необходимости — «не записывать страницы, содержащие…» для
   `/reserve` и `/register`.

## 8. Ecommerce

В init заявлено `ecommerce: "dataLayer"`. Анализ зависимости:

- `window.dataLayer` в приложении **не создаётся и не заполняется** —
  ни один компонент не отправляет ecommerce-события;
- `purchase`/воронки не реализованы сознательно: сайт не продаёт,
  покупки происходят только офлайн в магазинах после проверки возраста;
  фиксация «информационных действий как состоявшихся продаж» была бы
  недостоверной и стимулирующей (15-ФЗ ст. 19, 38-ФЗ ст. 7).

Настройка оставлена без изменений (безопасно: без dataLayer она инертна)
— на случай будущих **юридически подтверждённых** сценариев (например,
учёт офлайн-резервов в обезличенном виде после решения юриста). Удалять
не нужно; форсировать — запрещено до юридической оценки.
